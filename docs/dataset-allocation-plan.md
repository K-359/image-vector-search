# 新規学習・評価データの件数・配分案

作成日: 2026-09-20
更新日: 2026-09-24

検索条件を先に定め、元画像群から学習・評価データを最初から作るための第1段階です。
この文書は件数の設計案です。画像の選定やデータ生成はまだ実行していません。
上記は設計時点の状態です。続く実装と試行については[新規データ処理](condition-data-pipeline.md)を参照してください。
全検索条件への対応を優先し、工程別の実測時間を踏まえて規模を決めます。ユーザーは、生成に1日かかっていないことを確認したうえで、1,000枚を超える規模も許容しています。
「1,000枚で1日ちょっと」はユーザーの記憶であり、画像生成工程の実測時間とは区別します。保存ログの内訳は第7節に記載します。
条件別の目標件数と画像の選び方は、[画像配分と選定手順](image-selection-plan.md)で具体化しました。基本136条件は正例50・10・20枚、組み合わせ等71条件は20・5・10枚、評価専用20条件はtest正例20枚を目標とします。
今回の新規データ作成は、重複を除いた元画像5,000枚とします。内訳は学習3,500枚・検証500枚・評価1,000枚です。試行用50枚も5,000枚に含めます。
所要時間を測る前に、この枚数で実行時間や全条件の充足を保証しません。

## 1. 件数の単位

| 単位 | 数え方 |
|---|---|
| 意味の異なる検索条件 | 「右側の自転車」と「左側の自転車」は別。「右に自転車がいる」と「自転車が右にいる」は同じ |
| 条件ごとの正例画像数 | その条件を満たす異なる元画像の数。同じ画像の言い換えや複製で増やさない |
| 画像の総数 | 全条件の正例・負例に使う画像IDの重複を除いた数。条件別画像数の単純合計とは異なる |
| 学習ペア数 | クエリと画像の組の数。同じ意味・同じ画像の重複は件数を水増ししない |
| 評価クエリ数 | 同じ候補集合では同じ意味のクエリを統合して数える。正例画像が5枚あっても5クエリと数えない |

既存のS01〜S32は要求の具体例です。その32文を大量に言い換える設計にはしません。
種類・色・左右・道路環境などの条件値を展開し、意味の異なる条件を明示的に選びます。

## 2. 基本部分の検索条件配分

各条件には集計用の主分類を1つ付け、下表の重複をなくします。用途タグ・補助分類は複数付与できます。
表の条件数は生成する文の数ではなく、[検索条件一覧 v1](search-condition-catalog.md)で固定した意味の異なる検索条件の数です。

| 主分類 | 条件数 | 条件の選び方 |
|---|---:|---|
| 対象物の存在 | 7 | 車・バス・トラック・バン・歩行者・自転車・バイクを各1条件 |
| 対象物の色 | 24 | 歩行者を除く6種類×白・黒・赤・青の4色。歩行者の服色は車体色と混在させない |
| 画面内の位置 | 21 | 7種類×左・中央・右 |
| 道路・自車との位置関係 | 27 | 車両6種類×同一・左隣・右隣・対向の4車線で24条件、歩行者×歩道・横断歩道・車道で3条件 |
| 向き | 12 | 車両6種類×正面・背面。動いているとは要求しない |
| 道路・設備・路面 | 16 | 市街地・住宅街・高速道路・田舎道・トンネル内・橋上、交差点・横断歩道・工事区間・赤/青/黄信号・濡れた路面・積雪路面・カーブ・坂 |
| 時間帯・天候 | 8 | 昼・夜・薄明、晴れ・曇り・降雨・降雪・霧 |
| 2種類の対象物の共存 | 21 | 基本7種類から異なる2種類を選ぶ組み合わせ。順番の入れ替えは重複として扱う |
| 複数条件の組み合わせ | 64 | 環境＋対象＋必要に応じて位置を24条件、1対象の複数属性を16条件、複数対象への属性の結び付けを24条件 |
| **合計** | **200** | 主分類は重複なし |

「複数条件の組み合わせ」64条件は、検索条件一覧のCE01〜CE24・CA01〜CA16・CB01〜CB24として固定しました。
夜の横断歩道上の歩行者、同一車線の正面向き自転車、赤い車と白いバスを含みます。
対象物・色・位置の値を教師モデルに自由選択させず、条件一覧から指定します。

これは今回扱う条件の内訳です。画像の目標配分は[条件別CSV](search-condition-allocation.csv)に固定しましたが、出現頻度を再現した比率や、目標を必ず達成できる保証ではありません。
画像で成立を確認できない条件は不足として記録し、よくある車の条件などに無断で置き換えません。
未充足があれば条件数と件数の実績を明示し、必要に応じてこの案を更新します。

## 3. 初回は新規生成50枚で計測する

生成方式とスキーマを設計・実装した後、新たに選んだ50枚で動作と所要時間を測ります。
車だけに偏らず、歩行者・自転車・夜間・複数対象など、処理の難しさが異なる画像を含めます。
この試行も最初から作る新データの一部です。採用基準を満たし、生成仕様が変わらなければ初回セットに含めます。
仕様を変えて再生成する場合は、その時間も予算へ含めます。

測る項目:

- 画像候補の選定、画像認識、クエリ作成、正例・負例の判定、検証にかかる時間を工程別に記録する。
- 1画像あたりの平均・中央値・遅いケースの所要時間、出力長、失敗・再試行回数を測る。
- 条件ごとの採用画像数、クエリと条件の整合率、判定不能・棄却の割合を記録する。
- 画像1枚から信頼して利用できる検索条件が何種類得られるかを確認する。

50枚の所要時間を単純に比例拡大して確定値とはせず、画像難度、モデル読み込み、再試行、追加確認の時間を見込んで本生成の見積もりを作ります。

## 4. 今回の規模と分割

| 項目 | 今回の設定 |
|---|---|
| 教師モデルで新規に事実を抽出する元画像 | 重複を除いた5,000枚。試行50枚を含む |
| 学習・検証・評価の画像配分 | 3,500 / 500 / 1,000枚。撮影系列・近似画像が分割をまたがないように選ぶ |
| 選定方法の配分 | 条件を狙う4,000枚（2,800 / 400 / 800）＋無作為1,000枚（700 / 100 / 200）。試行50枚はtrain内の40＋10枚 |
| 条件ごとの画像数 | 基本136条件の正例50 / 10 / 20枚、組み合わせ・希少対象・追加判定の71条件は20 / 5 / 10枚、評価専用20条件は0 / 0 / 20枚。確認済み負例の目標を含む詳細は[選定手順](image-selection-plan.md)を参照 |
| クエリ数 | 画像に根拠のある条件から生成し、意味の重複を管理する。現時点で固定しない |
| 学習・検証ペア数 | 条件別の正例・確認済み負例から決め、画像数とは別に学習時間を見積もる |
| 未充足条件 | 条件別の不足一覧に残す。全条件を達成したとは扱わない |

全条件の充足を目標に、生成時間と学習時間を分けて見積もります。
画像の予備選別にも同じ高コストのモデルを使えば時間が増えるため、採用画像だけでなく選別・棄却・再試行も計測します。
評価候補や追加検証で新たに画像を教師モデルへ渡す場合も、別枠の無償処理として扱わず総時間へ含めます。

初回は、全カテゴリをなるべく含む画像を選び、同じ画像で複数の検索条件を扱えるようにします。
同一画像の共有は同じsplit内に限り、撮影系列・近似画像を含む分割漏れを避けます。
画像の共有によって条件別の学習事例は増やせますが、独立した画像数が増えたとは数えません。

## 5. 高コストの画像処理と条件別のデータ作成を分ける

新方式では、画像を教師モデルへ渡して確認した事実を保存し、その事実を複数の検索条件に利用できる設計を検討します。
例えば、1枚に「夜」「右側の自転車」「横断歩道」が確認できれば、それぞれの条件と明示的な組み合わせの候補にできます。
すでに確認できた事実の範囲では、条件ごとに同じ画像を読み直す処理を避けます。

既存の実装も画像1枚から複数クエリを生成しており、この分離だけで大幅に高速化できるとは主張しません。
主な狙いは、条件数に比例して画像認識の呼び出し回数が増える設計を避けることです。
クエリの言い換えや組み合わせを増やすだけで学習の多様性が十分になるとは扱いません。

画像側の構造化事実から、指定条件に合うクエリ・ペアを構成する方法を設計します。
画像に存在するか不明な対象や、取り出していない属性については、再確認するか判定不能として分離します。
カードへの未記載を不在とみなして負例を大量生成することはしません。
LLMによる文章生成、画像の再確認、独立した評価ラベルの確認にも時間がかかるため、それぞれ見積もります。

## 6. 条件の網羅性と評価の扱い

基本200条件に加え、評価専用の組み合わせ20条件、希少対象3条件、追加判定方式4条件、危険行動6条件を、[検索条件一覧 v1](search-condition-catalog.md)の計233条件として固定しました。
静止画で扱う候補は227条件、追加情報待ちは6条件です。条件ごとの画像配分は[条件別CSV](search-condition-allocation.csv)に保存しています。
各条件の必須条件・要求例との対応・評価専用条件の除外規則は一覧を参照してください。

- 初回に成立例が得られた条件、学習・評価の両方へ配置できた条件、画像や情報が足りない条件を分けて報告する。
- 評価専用の組み合わせは、構成要素が学習に存在することを確認してから評価枠にする。対象の組み合わせを含むクエリは言い換え・条件の追加を含めtrain/valから除外する。学習画像にその場面が写ること自体は禁止せず、視覚的に未経験の場面の評価とは区別する。初回で20条件を揃えることを強制しない。
- 同じ意味のクエリを正例画像ごとに複製し、評価クエリ数を水増ししない。
- 全体平均に加え、対象物・条件別の結果と件数を示す。少数例の条件の精度を確定的に扱わない。
- 初回で確認できなかった条件を、別の頻出条件や関連する静止画で置き換えて達成済みとしない。

本番の初段検索上位50件を評価する場合、クエリ数×50の判定が別途必要になります。
例えば220クエリなら11,000件であり、これを初回の必須作業としては固定しません。
少数のカテゴリ横断的な評価クエリから確認工数を測り、評価規模も総時間内で設計します。
独立に確認した評価と、合成ラベルによる開発用の評価は区別して結果を報告します。

動画・道路情報が必要な危険行動6条件は、必要な情報と判定方法が揃うまで未対応として残します。
要求範囲には保持しますが、静止画の処理枚数を増やすだけでは充足できません。
初回実験の完了と、全検索条件を満たす最終目標の達成を区別します。

## 7. 時間見積もりの根拠

保存ログの工程別時間を参考値として用います。同じ工程・同じ速度なら画像処理の部分は概ね枚数に応じて増えますが、新方式の速度は未計測です。

参考として、保存された `created_at` の最初から最後までの時間幅は、旧版のカード1,000枚で約5.44時間、Qwen3.8版で約2.64時間でした。
これらはカード生成の時間幅であり、候補選定・他工程・確認作業を含むデータ作成全体の所要時間ではありません。
この値を根拠に「1,000枚なら数時間で終わる」とは見積もりません。

| 記録された工程 | 旧版 | Qwen3.8版 |
|---|---:|---:|
| カード1,000枚の先頭〜末尾の時刻差 | 5時間26分37秒 | 2時間38分24秒 |
| 学習 `elapsed_seconds` | 14,124.8秒（約3時間55分） | 15,602.1秒（約4時間20分） |
| test評価のbaseとadapterの `elapsed_seconds` 合計 | 1,843.9秒（約31分） | 2,132.3秒（約36分） |

旧版は最初のカード保存（日本時間8月10日18:17）からtest評価レポート保存（8月11日22:40）まで約28時間23分です。
この時間差には工程間の待ち時間等も入りうるため、連続した計算時間とは扱いません。
「1日ちょっと」はこの全工程の経過時間を指す可能性がありますが、ユーザーの記憶との対応は未確認です。
上記の工程別記録だけでも準備・読み込み・別の実行等をすべて網羅したわけではありません。

Qwen3.8版の学習は7,292ペアを2エポックで約4時間20分でした。
同じモデル・解像度・出力長等なら、画像の事実抽出は新規画像数と呼び出し回数、学習は重複除去後のペア数とエポック数が時間の主な見積もり単位になります。
この実績を単純に比例拡大すると、ラベル付け5,000枚は約13.2時間、学習40,000ペアを2エポックなら約23.8時間です。
これは別々の工程の概算であり、5,000枚から必ず40,000ペアを作るという計画でも、新方式の実測でもありません。
ラベル付けには構造化事実とクエリの生成が含まれます。将来追加する独立した検証や人手の評価注釈は、この生成時間とは別に見積もります。


また、旧案の16,400は条件別の正例画像数を合算した値であり、重複を除いた実画像数ではありませんでした。
したがって、その値をそのまま16.4日と換算することもできません。
新規生成する実画像数、LLM呼び出し回数、採用率、確認作業量から見積もり直します。

## 8. 次の作業

検索条件一覧と[画像配分・選定手順](image-selection-plan.md)は固定しました。次は複数条件に利用できる画像事実と判定不能のスキーマを設計し、候補選定から試行までを実装します。
既存の画像索引はありますが、検索用の実行環境・元索引の生成仕様の確認はまだ必要です。
その後に新方式でtrainの50枚を試行し、品質と処理時間を確認して、今回の5,000枚へ進みます。
この文書の更新時点では、モデル呼び出し・画像生成・学習・評価は実行していません。
以前の生成済みラベルを修正する作業は、新規構築の前提にしません。

# 言い換えクエリの学習と、教師に依存しない評価

評価日: 2026-09-26〜29

[条件指定データの評価](condition-eval.md)では、クエリがtrain/val/testで同じ基準文で、ラベルもすべて教師モデル（Qwen3.8）の判定でした。
ここでは作り方を1本に保ったまま、次の5点を確認しました。

1. 条件ごとに言い換えた文で学習・評価しても性能が保たれるか（文型への過学習がないか）
2. 教師に依存しない正解（BDD100K の公式人手ラベル）で比べても、v3 方式が v2 方式（教師が自由にクエリを書く方式）より広く効くか
3. 学習した条件より長い、3〜4条件の組み合わせのクエリにも効くか
4. 条件一覧を見ずに書かれたクエリを、条件一覧の語彙でどれだけ表せるか
5. 見つかった穴を同じ手順で埋められるか（条件一覧の拡張）

## 当初の課題への答え

v1・v2 では、1,000枚の画像に対して教師が自由にクエリを書いていました。
そのため学習・評価データが偏り、事実上、特定のクエリだけを学習・評価していました。
v3 はこれに対し、条件一覧でクエリの分布を設計し、ラベルを条件の判定から付ける作り方です。

**偏り**: 学習クエリが何を求めているかを数えると、次のとおりです（`scripts/compare_query_distribution.py`）。

| | v2（自由生成） | v3（条件一覧＋言い換え） |
|---|---:|---:|
| 学習クエリ | 1,152 | 1,135（204条件） |
| 学習画像 | 689 | 3,500 |
| 車を含む | 79.1% | 21.3% |
| トラック／バン／バスを含む | 9.1% / 8.7% / 4.3% | 14.2% / 13.0% / 15.8% |
| 歩行者／自転車／バイクを含む | 4.7% / 1.2% / 0.3% | 14.1% / 15.7% / 15.0% |
| 対象が車だけ | 70.3% | 11.2% |
| 対象なし（場面だけ） | 2.3% | 13.0% |

- v2 は車・後ろ向き・自車線に集中していました（それぞれクエリの79%・57%・57%）。
- v2 の test（336クエリ）も同じ作り方なので、75%が車を含み、66%は対象が車だけです。
- v3 は1条件あたりのクエリが最大0.7%で、条件ごとのペア数も70件で頭打ちにしています。

**特定のクエリだけの評価**: v2 アダプタが強いのは、同じ教師が作った v2 test の中だけでした（[2節](#2-v2-test-との相互評価について)）。
教師に依存しない BDD の人手ラベルでは、v3 方式が v2 方式を上回りました（[3節](#3-bdd100k-公式ラベルによる評価)・[4節](#4-34条件の長いクエリ)）。
差が大きいのは、位置の結び付け・2対象の共存・画面位置です。これらは v2 でほとんど学習されていなかった条件でした。

**残る限界**: 偏りが消えたのではなく、設計で制御できるようになった段階です。

- 学習できる範囲の上限は、条件一覧で決まります。
- 一覧で定義していない語（「前方」、夜の「晴れ」）では、教師と評価側の定義がずれて性能が落ちます。今回見つかった弱点は、すべてこの種類でした。
- 条件一覧を見ずに書かれたクエリのうち、今の語彙で表せるのは7〜9%でした（[5節](#5-条件一覧の網羅率)）。表せない主な理由は、次の2つです。
  - 「停車している」「走っている」など動きの語（約8割）
  - 一覧にない色・車種（約3割）
- したがって、課題は作り方から、条件一覧の中身をどこまで広げるかに移っています。
- 駐車と黄・緑を同じ手順で足すと、表せる割合は15〜24%になり、既存の条件の性能は落ちませんでした（[6節](#6-条件一覧の拡張v4)）。

## 作り方の変更点

- 教師LLM（Qwen3.8）が**画像を見ずに**、条件一覧の必須条件から言い換えを最大10件生成します（`scripts/generate_condition_queries.py`）。
  - 用語集で許す言い換えを固定しました。例えば「前方」は「自車と同じ車線」の言い換えとして扱い、「車両」「二輪車」のように種類があいまいな語は使いません。
  - 動きの語（走る・停まる）は使わず、条件にない対象や場面を足して件数を埋めないよう指示します。
- 生成文は、同じ教師がクエリ文だけを見て条件へ戻す逆変換で検証し、欠落・付け足し・依頼文（「探して」など）・重複を除きます。223条件で1,946件を生成し、1,649件（85%）が合格しました。
- 正解ラベルは文ではなく条件の判定から付けるので、画像とラベルは v3 のまま変わりません（`scripts/build_paraphrase_pairs.py`）。
  - 各条件の言い換えの3割（最大3件）を test 専用にし、残りと基準文を学習に使います。学習ペア数は v3 と同じ11,072件です。
  - test は同じ画像・ラベルに対し、test 専用の言い換え537クエリ（12,931ペア）で採点します。

## 1. 言い換えへの汎化

学習条件は v3 と同じです（QLoRA 4bit、rank 32、2エポック、2026-09-26 20:25〜09-27 03:00 JST、val nDCG@5 0.978）。
「旧」は基準文だけで学習したv3アダプタ、「新」は言い換えも学習したアダプタです。

| test | base | 旧 | 新 | 新−旧（95%CI） |
|---|---:|---:|---:|---|
| test 専用の言い換え（537クエリ） | 0.776 | 0.976 | 0.983 | +0.007 [−0.001, +0.017] |
| 基準文（207クエリ） | 0.792 | 0.982 | 0.984 | +0.003 [−0.004, +0.010] |

指標は nDCG@5、ラベルは教師の判定です。

基準文だけで学習した旧アダプタも、未学習の言い換えにほぼ汎化していました。
例外は、条件一覧にない語で定義を持つものです。車線の条件（LOC）を表現別に分けたクエリ内AUCは次のとおりです。

| 表現 | クエリ数 | base | 旧 | 新 |
|---|---:|---:|---:|---:|
| 「前方」 | 7 | 0.710 | 0.669 | 0.857 |
| 「自車線」「同じ車線」 | 5 | 0.580 | 0.799 | 0.929 |
| 「反対車線」 | 3 | 0.344 | 0.908 | 0.936 |
| その他 | 58 | 0.646 | 0.951 | 0.947 |

旧アダプタは「前方」で学習前より悪くなり、言い換えで定義を学ぶと回復しました。
ただし件数が少ないので、傾向として扱います。

## 2. v2 test との相互評価について

v2 test（325クエリ）での nDCG@5 は、base 0.865、v2 0.917、v3 0.831、v3言い換え 0.832 でした。
ただし、この比較は中立な判定になりません。

- v2 のクエリの82%が動きの語を、42%が「前方」を含みます。v3 で対象外にした語を1つも含まないのは46件だけです。
- v2 の正解ラベルは、教師のキャプションとクエリ条件を文字列で照合したもの（`scene_card_constraint_match_v1`）です。上位に来た不正解の画像を目で見ると、前方の別車線にいる白いバンや、前方の銀色の車が「不適合」とされていました。「前方左側」が正例になっている例もありました。
- つまり v2 test は、v2 の教師の定義にどれだけ一致するかを測っています。

## 3. BDD100K 公式ラベルによる評価

教師を使わない正解として、BDD100K の公式アノテーションを使いました（`scripts/build_bdd_eval.py`）。

- 対象画像: 人手ラベルがあり、v1〜v3 のどの split でも使っていない75,121枚です。
- ラベル: BDD の物体の枠・信号の色・横断歩道の標示線・シーン属性を v3 と同じ事実の形式に変換し、v3 と同じ判定コード（`condition_data.evaluate`）で条件を判定します。
  - 高さ20px未満の枠は小さすぎて判定できないものとして扱います。すべての枠を使った判定と大きい枠だけの判定が食い違えば、判定不能にします。
  - BDD にない属性（色・向き・自車線・バン・橋・カーブなど）は判定不能となり、その条件は評価から外れます。
- 候補: test 専用の言い換えで10万枚の索引を初段検索し、対象画像の上位50件を再ランキングします。本番と同じ設定です。
  - X01〜X04 は言い換えがないため、基準文を使います。
  - 判定不能の候補は除きます。
- 規模: 判定できた80条件のうち、正例と負例の両方がそろった73クエリ・3,453ペアです。

画像を確認して見つかった BDD 側の定義のずれには、次のように対処しました。

| 条件 | BDD のラベル | 扱い |
|---|---|---|
| トンネル内 | トンネル内でも道路の種類（highway など）が付くことがある | トンネル以外のラベルを負例の根拠にしない |
| 霧・雨 | 霧や、フロントガラスの雨粒が見える画像にも overcast が付くことがある | 負例の根拠は clear（雨・霧は partly cloudy も）だけにする |
| 降雪 | snowy は積雪を指し、降っている雪とは限らない | 評価しない |
| 自車線 | 走行可能領域（direct）が車線のない道路全体を覆い、歩道の自転車や路肩の駐車車両まで含む | 評価しない |
| 市街地・住宅街 | 1枚に1つしか付かない | 互いを負例の根拠にしない |

## 4. 3〜4条件の長いクエリ

条件一覧の条件は1〜3個の制約から成り、学習した言い換えも短い文です。
そこで、BDD で判定できる制約を3〜4個組み合わせた条件を作り、長いクエリで評価しました（`scripts/build_combo_conditions.py`）。
アダプタは3節と同じで、再学習はしていません。

- 制約: 時間帯、晴れ・雨、道路の種類、横断歩道、信号の色、対象の種類（バス・トラック・歩行者・自転車・バイク）、画面位置です。
  - 車は BDD 画像の97%に写っていて絞り込みにならないため、除きました。
  - 2つの対象は、位置を両方に付けるか、どちらにも付けないかのどちらかにしました。「画面左に歩行者、自転車」では、位置がどこまでかかるか読めないためです。
- 組み合わせは実際の画像から抜き出すので、正例は必ずあります。
  - 対象画像の0.05〜15%に当てはまるものだけを残しました。
  - 条件一覧と同じ組み合わせは除きました。
- 3条件と4条件を40件ずつ作りました。教師が画像を見ずに条件ごとに最大5件の文を作り、逆変換の検証に通った文（303/340件、89%）から1件を固定の順序で選んで使います。
- 候補とラベルの付け方は3節と同じです。規模は80クエリ・3,666組です。

nDCG@10 は次のとおりです（`scripts/analyze_combo_eval.py`）。

| 区分 | クエリ | base | v2 | v3 | v3言い換え | v3言い換え − v2（95%CI） |
|---|---:|---:|---:|---:|---:|---|
| 全体 | 80 | 0.657 | 0.744 | 0.809 | 0.810 | +0.067 [+0.019, +0.117] |
| 3条件 | 40 | 0.747 | 0.820 | 0.877 | 0.882 | +0.062 [+0.020, +0.104] |
| 4条件 | 40 | 0.568 | 0.667 | 0.742 | 0.739 | +0.071 [−0.014, +0.162] |
| 位置を含む | 33 | 0.542 | 0.722 | 0.823 | 0.822 | +0.100 [+0.040, +0.162] |
| 対象が2つ | 8 | 0.473 | 0.566 | 0.788 | 0.833 | +0.267 [+0.103, +0.477] |
| 場面の条件だけ | 18 | 0.661 | 0.701 | 0.728 | 0.734 | +0.033 [−0.072, +0.155] |
| 晴れを含む | 24 | 0.674 | 0.723 | 0.750 | 0.773 | +0.050 [−0.047, +0.149] |
| 晴れを含まない | 56 | 0.650 | 0.752 | 0.835 | 0.826 | +0.074 [+0.020, +0.133] |

- 4条件ではすべてのモデルが下がりますが、base との差は保たれています（v3言い換え − base: +0.171 [+0.074, +0.270]）。
  - 4条件のクエリ内 AUC では、v3言い換え − v2 が +0.063 [+0.022, +0.106] で有意でした。
- 対象や位置を含む長いクエリには、短いクエリだけの学習でも汎化していました。
- 弱いのは「夜・晴れ」の組み合わせで、AUC が低い条件の上位は「夜・晴れ・高速道路」「夜・晴れ・市街地・青信号が見える」などでした。
  - v3 の教師は、夜の画像1,439枚で一度も晴れと判定していません（`annotations/facts.jsonl`）。条件一覧が「空が見えないときの天候は不明」としているためです。
  - 一方、BDD は夜でも雨でなければ clear と付けます。
  - v3 系は「晴れ」を「明るい昼の晴天」として学んでいると考えられます。3節で天候の区分だけ伸びなかったことも、これで説明がつきます。
  - これは「前方」と同じく、教師と評価側の語の定義のずれです。クエリの長さによるものではありません。

## 5. 条件一覧の網羅率

1〜4節の評価クエリは、どれも条件一覧か同じ語彙から作ったものです。
そのため、評価の問題の分布は v3 の学習の分布に近く、v3 に有利な可能性があります。
そこで、条件一覧を見ずに書かれたクエリが一覧の語彙で表せるかを数えました（`scripts/measure_catalog_coverage.py`）。
画像の正解ラベルは使いません。

- 対象: v1 test（Qwen3.6 が画像を見て自由に書いた301件）と v2 test（Qwen3.8 が書いた336件）のクエリ文
- 判定:
  1. 言い換えの検証に使う逆変換（`generate_condition_queries.verify` と同じ呼び出し）で、文を条件の語彙へ戻します。
  2. 語彙で表せないとされた部分（`other`）を、規則で種類に分けます。
  3. 逆変換は表せない語を黙って落とすことがあります。例えば「緑色のバン」は、色なしのバンになります。そのため、動き・色・車種・台数の語は文そのものからも検出します。

| | v1 test | v2 test |
|---|---:|---:|
| 条件一覧の条件と完全に一致 | 1.7% | 0.0% |
| 今の語彙で表せる | 9.3% | 6.8% |
| 動きの語を除けば表せる | 65.4% | 59.2% |
| さらに一覧にない色・車種を除けば表せる | 83.4% | 80.7% |

表せない部分の内訳は次のとおりです（1件に複数あり）。

| 表せない部分 | v1 test | v2 test | 例 |
|---|---:|---:|---|
| 走行などの動き | 51.5% | 50.9% | 走っている、自車へ向かって走行、並走 |
| 停止・駐車 | 33.6% | 39.6% | 停車している、路肩に駐車している |
| 一覧にない色・車種 | 26.9% | 30.4% | セダン、SUV、タクシー、銀色、黄色、緑色 |
| 種類があいまいな対象 | 8.0% | 8.6% | 車両、三輪タクシー、ドラム型コーン |
| 一覧にない場所・設備 | 4.3% | 1.2% | 高架下、路肩、ガードレール |
| 自車より後ろ・対象同士の位置関係 | 2.3% | 2.7% | 自車の後方、トンネル手前、並んでいる |
| 台数 | 1.0% | 0.6% | 人々、2台 |
| その他 | 3.0% | 9.8% | 幹線道路、ハッチバック、立っている |

- 条件一覧の条件そのものは、ほとんど出てきませんでした。それでも4節のとおり、v3 は一覧にない組み合わせにも効きます。問題になるのは組み合わせではなく、語彙の範囲です。
- 走行などの動きを抜き取りで40件見たところ、多くは次のような飾りの語でした。
  - 「同じ車線を走る白い車」のように、車線や向きで表せる内容を言い直しているもの
  - 「道路を走行している車」のように、ほぼ何も絞り込まないもの
- 停止・駐車は、「路肩に駐車している」のように実際に絞り込む条件です。ただし1枚の画像では、停車中か低速走行中か区別しにくいことがあります。
- 色・車種のうち、銀色と車種の細分類は、あいまいさを理由に対象外にしたものです。黄色・緑色・タクシーは判定しやすく、追加の候補になります。
- 条件一覧を広げるには、画像の事実のスキーマに項目を足して、事実の注釈をやり直す必要があります。
  - 今の事実には停車・駐車の項目がなく、色も白・黒・赤・青・その他だけです。
  - v3 の5,000枚の注釈には約23時間かかりました。

この測定の限界:

- 対象のクエリも教師 LLM が書いたもので、実際の利用者のクエリではありません。v2 の教師が「停車」を多用するなど、教師の癖が入っています。
- 逆変換と分類規則には誤りがあります。例えば「街路」を表せない語とした例や、「進行している」の動きを見落とした例がありました。上の割合は目安です。

## 6. 条件一覧の拡張（v4）

5節で見つかった穴のうち、画像1枚で判定でき、実際に絞り込む条件になる2つを、同じ手順で埋めました。

- 追加した語彙: 駐車している乗り物、黄色・緑色の乗り物
- 追加した条件: 25条件（[拡張カタログ](../search-condition-catalog-extension.md)）
  - test 専用の未学習の組み合わせ3条件（H21〜H23）を含みます。

### 作り方

v3 の条件・画像・ラベルは変えず、事実を追記しました。

1. **追加の注釈**（`scripts/annotate_extension_facts.py`）
   - v3 の5,000枚で、記録済みの乗り物に番号付きの枠を描き、同じ教師に「駐車か」「黄・緑か」だけを判定させました。
   - 1枚あたり約5秒、計6.5時間でした。v3 の注釈を一からやり直すと約23時間かかります。
   - 4,995枚で成功しました。
   - 試しの12枚を目で確認したところ、遠くの小さい車にも自信のある答えを返していました。そこで、高さ20px未満の枠は判定不能にしました（BDD 評価と同じ基準です）。
2. **言い換えの生成**
   - 用語集に黄・緑・駐車を足し、画像を見ずに言い換えを作って、逆変換で検証しました（`generate_condition_queries.py --extension`）。合格は182/214件（85%）です。
   - v3 のプロンプトは変えていないことを、ハッシュで確認しました。
3. **ペアの作成と学習**
   - ペアの作成と言い換えの割り当ては v3 と同じコードです（`scripts/build_extension_dataset.py`）。
   - 学習データは、v3 言い換えの学習データに新しい条件の1,105組を足した12,177組です。
   - 学習の設定は v3 と同じで、val nDCG@5 は0.972でした。

正例の数（train）は、駐車している車が1,520、黄色い車が173でした。緑色は8〜13と少なく、H23（画面右の黄色いバス）は test の正例が1件しかありません。

### 解釈

- 見つかった穴を、同じ手順で埋められました。
  - 必要だったのは、条件一覧の追加、足りない事実だけの追加注釈、言い換えの生成、再学習です。
  - 表せるクエリの割合は約2.5倍になり、既存の条件の性能は落ちていません。
- ただし、学習による上積みは小さいです。v3 言い換えのアダプタは、駐車・黄・緑を学習していないのに、新しい条件で base を大きく上回りました（0.582→0.934）。
  - 考えられる理由は2つです。
    - 車線・歩道・画面位置など、関連する条件の学習が効いた可能性。
    - 同じ教師の判定に合わせる学習そのものが、教師の新しい判定にも効いた可能性。
  - 新しい条件の正解は教師の判定だけです（BDD には駐車も黄・緑もありません）。後者の可能性は否定できません。

## 考察

- 教師に依存しない正解でも、v3 方式は v2 方式より明確に良い結果でした。差が大きいのは位置の結び付け・共存・画面位置・数や不在の判定で、自由生成の v2 では学習事例が偏っていた組み合わせの条件です。
- 道路の種類・天候では差がありませんでした。ただし「市街地」「高速道路」などは上位50件の負例が1〜2件しかなく、この区分の比較は弱いです。
- 言い換えを学習しても、基準文・言い換え・BDD のいずれでも性能は落ちていません。「前方」のように定義を持つ語はむしろ改善しました。言い換えを含む作り方を標準にします。
- 条件一覧にない3〜4条件の組み合わせにも効いたので、長いクエリ専用の学習データは今のところ必要ないと判断します。
- 条件一覧の穴は、事実の追記と条件の追加という同じ手順で埋められました（6節）。ただし、新しい語彙での上積みは教師ラベルでしか測れていません。

## この評価の限界と今後の課題

- BDD で判定できるのは233条件のうち80条件です。色・向き・自車線は、引き続き教師ラベルによる評価だけが根拠です。
- BDD の人手ラベルにも誤りや定義の違いがあります。見つけたずれには対処しましたが、確認したのは抜き取りです。
- 実際の利用者がどのようなクエリを書くかは分かっていません。教師が自由に書いたクエリで測ると、今の語彙で表せるのは7〜9%（拡張後15〜24%）、動きの語を除けば約6〜7割でした（5・6節）。
- 駐車・黄・緑の正解は教師の判定だけです。v3 のアダプタがこれらを学習せずに高い点を取った理由を切り分けるには、教師に依存しない正解が必要です。
- 条件一覧にない語をどう拾うかが、次の課題です。
  - 「前方」は用語集で定義して言い換えを学習させると回復しました。
  - 夜の「晴れ」は、条件一覧の定義を「夜は天候を問わない」とするか、BDD に合わせるかを決める必要があります。

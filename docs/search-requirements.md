# 検索要求と正解判定基準（初版）

作成日: 2026-09-20

[検索条件の分類](search-condition-taxonomy.md)を、データ作成時に選べる具体的な要求へ落とした一覧です。
一般的な交通シーン（U01）、安全確認（U02）、危険場面（U03）のすべてを対象とします。
以下は設計例であり、実画像に対する確認済みラベルや完成した評価セットではありません。
記載した要求は網羅性を確認する最初の単位であり、各要求につきクエリを1件だけ作るという意味ではありません。
2026-09-24に、これら42件の例を含む[検索条件一覧 v1（233条件）](search-condition-catalog.md)を固定しました。画像選定ではその条件IDを使い、この文書を共通の判定規約として参照します。

## 1. 全要求に共通する注釈規約

### 適合・不適合・判定不能

- **適合**: クエリの必須条件をすべて確認できる。記載されていない色、時間帯、天候、動きは問わない。
- **不適合**: 必須条件が成立しないことを確認できる。下表の負例候補も、画像内の別の対象がクエリを満たしていないか確認してから採用する。
- **判定不能**: 不鮮明、遮蔽、意味の曖昧さ、必要な情報の欠落などにより適合・不適合を確定できない。二値の学習・評価セットにはそのまま投入しない。

条件の各判定を記録してから画像全体の判定を決めます。
ANDは全条件が適合なら適合、少なくとも1条件が確実に不適合なら不適合、それ以外は判定不能です。
対象物の属性は対象ごとにまとめて判定します。赤いバスと白い車から「赤い車」の適合を作ってはいけません。
ORは少なくとも1条件が適合なら適合、すべて不適合なら不適合、それ以外は判定不能です。
否定条件は、対応する肯定条件が適合なら不適合、不適合なら適合、判定不能なら判定不能です。

### 観察範囲と表現の境界

- **観察範囲**: 元画像の全画面を確認し、必要に応じて拡大する。対象は画像内で視認できるものとし、画面外や完全な遮蔽の裏にいる対象までは要求しない。教師のシーンカードへの記載の有無で不在を判定しない。
- **対象の不在**: 全画面を確認しても対象がない場合に判断する。対象かもしれない小さい像・部分像を識別できない場合は判定不能とする。画像全体が確認に適さない場合も同様。
- **対象の種類**: この一覧の「車」は `car`（乗用車）を指し、バス・トラック・バンとは分ける。「車両」という上位概念を使うクエリは、対象範囲を別途定義する。車とバンなどの境界が不明なら判定不能とする。
- **人と乗り物**: 自転車・バイクに乗っている人を歩行者として数えない。自転車を押して歩く人は歩行者と自転車の両方として扱う。自転車・バイクは乗り手の有無を問わない。
- **左右**: 初版の注釈案は画面を横に3等分し、対象の可視範囲を囲う矩形の中心が入る区画を左・中央・右とする。区画境界上または遮蔽により中心を安定して決められないものは判定不能とする。実画像で人の解釈と合うか確認してから規約を固定する。
- **車線・道路上の位置**: 対象の接地点と車線・歩道等の境界を確認する。「画面右側」と「右隣の車線」は区別する。道路方向を推測して対向車線を付けない。
- **前方・近い・危険**: 初版の基準クエリでは、参照範囲や判断基準が未定義のまま使わない。単なる画面上の大きさを物理的な距離と同一視しない。
- **天候・路面**: 濡れた路面だけで降雨、積雪だけで降雪とは判定しない。薄明と夜、霧と煙・汚れなどを区別できない場合は判定不能とする。
- **信号色**: 「赤信号が見える」は視認できる車両用信号に赤の灯火があることを指す。自車に適用される信号か、車両が違反しているかは要求しない。

この規約の位置・対象種類・環境の境界は、注釈者間で実画像を確認して調整する初版案です。

### 具体的な条件一覧への展開

上記32件で全条件値を網羅したとは扱いません。以下も画像の充足状況を調べる対象です。

- 緊急車両、列車、動物の存在。
- 色と車種の入れ替え、左右・中央、歩道・路肩・隣接車線の入れ替え。
- 昼、薄明、晴れ、曇り、降雪、市街地、住宅街、高速道路、橋、交差点、信号色の違い。
- 夜×自転車、霧×歩行者、工事区間×自転車などの組み合わせ。

展開した条件と組み合わせは[検索条件一覧 v1](search-condition-catalog.md)に列挙しました。路肩など今回の一覧の外に残る要求候補も同文書で管理します。画像にない条件の強制生成は行いません。

## 3. 注釈・判定方法を追加する要求（4件）

| ID / 分類 | 基準クエリ | 適合する状況の例 | 紛らわしい負例候補 | 判定不能・必要な定義 |
|---|---|---|---|---|
| X01 / C01,C09 | トラックより画面上で左に歩行者がいる画像 | あるトラックと歩行者の組で、歩行者の中心が左にある | 歩行者がすべてのトラックの右側にいる | 対象ID・中心座標が必要。中心の左右を決められなければ判定不能 |
| X02 / C01,C10 | 車がちょうど2台見える画像 | 識別できる乗用車が2台だけある | 乗用車が1台または3台ある | 遠方・部分像に追加の乗用車候補があり種類を決められない |
| X03 / C01,C10 | 歩行者が写っていない画像 | 全画面を確認して歩行者がいない | 歩行者が1人以上見える | 人らしい影があるが識別できない。カードの無記載だけでは適合にしない |
| X04 / C01,C10 | バスまたはトラックがいる画像 | バスかトラック、または両方が見える | バンだけが見える | 両方の不在を確定できず、適合する対象も確認できない |

X01の「左」は画像座標を指し、トラック自身の進行方向に対する左ではありません。
X02は画像内の視認可能な乗用車の正確な数です。現状のシーンカードの最大記載件数から総数を判断しません。

## 4. 危険行動そのものの検索要求（6件）

D01〜D06はU03の要求です。静止画の関連条件を、行動の正解ラベルへ自動変換しません。
現状は「追加情報と判定規約の確認待ち」とします。「急」の閾値などは運用上の定義を決めてから正例・負例を確定します。

| ID | 基準クエリ | 適合判定に必要な根拠 | 紛らわしい負例候補 | 追加情報・未確定事項 |
|---|---|---|---|---|
| D01 | 逆走している自転車 | 自転車の実移動方向が、その走行位置で認められる方向に反している | 正面向きだが正規の対向通行をしている自転車 | 追跡可能な動画、走行位置、通行方向を示す情報。向きだけでは不明 |
| D02 | 車両の陰から歩行者が飛び出す場面 | 車両による遮蔽から歩行者が現れ、車両通行域へ進入する経過 | 歩行者が車両の横に立っているだけ | 出現前後の動画、遮蔽物、進入経路。「飛び出す」の時間・速度等の基準 |
| D03 | 歩行者が急に車道を横断する場面 | 歩行者の道路横断軌跡と、定義した急な開始・移動の条件を満たす | 横断歩道上に立っているだけ | 横断前後の動画、道路境界。「急」の判定基準 |
| D04 | 前方の車が急停止する場面 | 同一車両の移動から停止への変化が、定義した減速条件を満たす | 最初から停止していた車 | 時刻付き動画、カメラ自体の運動、速度・減速・停止の判定基準 |
| D05 | 自車に車両が急接近する場面 | 自車と対象車両の距離が、定義した接近速度・距離の条件を満たす | 近くにいるが相対距離がほぼ一定の車 | 時刻付き動画、距離・相対速度の根拠。「急接近」の判定基準 |
| D06 | 車が信号を無視して進む場面 | 対象車両に適用される信号、停止位置、通過時点の状態が判定規約に反する | 別方向の赤信号と、通行可能な車両が同時に見える | 動画、信号と車線の対応、停止線、対象地域・信号運用に合わせた注釈規約 |

必要な根拠がないものは未評価とし、適合率・再現率等の計算対象に混ぜません。
動画が利用できる場合も、既存の静止画検索にどう対応付けるか（代表フレーム、前後文脈など）は別途設計します。

## 5. 後続のデータ構築で記録する項目

各要求のデータには、少なくとも以下を関連付けます。これは設計項目であり、現在のJSONLへの追加実装はまだ行っていません。

| 項目 | 内容 |
|---|---|
| 要求ID・用途・分類 | S10、U01/U02、C01/C03など |
| 条件の組み合わせID | 対象・属性・関係・論理演算を正規化した意味上の識別子。言い換えでは同じIDを使う |
| クエリと必須条件 | 「画面右側に自転車」→自転車の存在、画面右側。同じ対象に結び付ける |
| 画像・動画の識別子 | 出典、撮影系列、元画像。近接フレーム等の分割漏れを防ぐために使う |
| 判定と根拠 | 適合・不適合・判定不能、対象位置、成立・不成立の条件、確認者 |
| 負例の違い | 種類だけ違う、位置だけ違う、色の対応が逆、など |
| 利用区分 | train/val/test、基本条件評価/未知の組み合わせ評価。固定した評価は学習へ混ぜない |

## 6. この一覧の次に行うこと

具体的な233条件は[検索条件一覧 v1](search-condition-catalog.md)で固定しました。この一覧を基に、学習・評価データを最初から作り直すための生成仕様を決めます。
第1段階の[件数・配分案](dataset-allocation-plan.md)では、意味の異なる条件数と各条件の画像数を分けて設計しています。
目標件数と選定方式は[画像配分と選定手順](image-selection-plan.md)に固定しました。以下の1は完了、2は方式の設計まで完了で、実画像の選定は未実施です。

1. 要求・対象物・組み合わせごとの学習／検証／評価の目標件数を設計する。
2. 元画像群から条件別に候補を選ぶ方法と、撮影系列・近似画像を考慮した分割方法を決める。
3. 検索条件を指定してクエリと画像の事実を新規生成し、クエリにない条件を混入させない検証を行う。
4. 正例と紛らわしい負例を構成し、判定不能を分離する。評価用のクエリ・正解は独立に確認して固定する。
5. 新しいデータセットとして保存し、QLoRA学習と評価へ進む。

以前の生成済みデータの修正・継ぎ足しを、この手順の前提にしません。
[既存データの監査結果](reports/search-coverage-review.md)は、新規生成で防ぐべき偏りやラベル不整合の参考情報です。
元画像の不足や外部からの追加収集の必要性はまだ確定していません。
